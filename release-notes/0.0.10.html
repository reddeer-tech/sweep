What's New

The space you got back, not the space we guessed

Sweep used to add up the size of everything it removed and report that as the amount freed. That number is an estimate, and on a Mac it can be badly wrong in a direction that looks like the app lying to you.

Three reasons it drifts:

  • Copy-on-write files share storage. Xcode clones its test and preview simulators using APFS cloning, so twenty clones can report twenty times the size while sharing almost all of it on disk. Measured: cloning a 300 MB file adds 300 MB to the size tool's total and zero bytes to the volume.
  • Docker keeps its own pool. Pruning images and build cache returns the space to Docker, not to macOS, so your free space may not move at all.
  • macOS holds deleted bytes as purgeable behind local Time Machine snapshots until something releases them.

Sweep now measures your actual free space before and after a clean and reports that. When the estimate was much higher, it says so and explains which of the above is responsible, instead of leaving you to wonder why Finder disagrees.

Dry runs now say "would free up to", because an estimate is all a dry run can honestly offer.

Xcode device clones are labelled honestly

The test, preview and playground clone sections are usually the largest thing Sweep finds on a developer's Mac — 171 GB on the machine this was built on. Those rows now state plainly that the figure is an upper bound, and that the real gain is usually smaller, sometimes much smaller.

They are still worth removing, and still left unchecked by default: a clone that can't boot is dead weight, but it holds whatever your test run wrote into it, so that stays your call.
